Flutter implementation plan — ManakSetu mobile demo
1. Objective

Build a fully hardcoded Flutter mobile prototype of ManakSetu for SIH demonstration purposes.

Nothing needs to contact the Python backend, Supabase, Gemini, APIs, or external databases.

The application must look and behave like a working standards-intelligence product, but every result can be represented by local Dart models and deterministic demo state.

The goal is:

Page 1
Tender / Requirement Scrutiny
        ↓
User enters requirement
        ↓
Hardcoded analysis result
        ↓
Standards + compliance findings + evidence
        ↓
Optional image upload → Text Clause Analyzer UI

Page 2
Specification Builder
        ↓
Selected standard
        ↓
Build technical procurement specification
        ↓
Clause-by-clause evidence
        ↓
Open exact BIS document/page

Do not attempt to reproduce the entire web PRD. The original product specification contains significantly broader functionality—multi-modal ingestion, hybrid retrieval, knowledge graph, regulatory guardrails, anti-tailoring, foreign-standard normalization, exports, etc.

For this phase, those are out of scope.

2. Technology

Use:

Flutter
Dart
Material 3
go_router
file_picker

No backend dependency.

No Firebase.

No Supabase.

No REST API.

No authentication.

No database.

No state-management framework unless genuinely necessary.

For a two-page demo, keep state local using ordinary Flutter state / controllers.

5. Hardcoded data architecture

Do not scatter strings throughout widget code.

Create proper Dart models.

For example:

class Standard {
  final String number;
  final String title;
  final String status;
  final String reason;
  final List<Evidence> evidence;
}

and:

class Evidence {
  final String sourceFile;
  final int page;
  final String? clause;
  final String text;
}

Then place all demonstration content inside:

data/demo_data.dart

The UI should render the data.

This is important because later you can replace:

DemoRepository

with:

ApiRepository

without redesigning the UI.

31. Critical implementation rule

Do not delete, modify, or depend on the existing web application.

Create the Flutter application independently.

The mobile demo should be able to run even if:

Python is not installed
backend is offline
Supabase is offline

That is exactly what you want for a hackathon demo.

Architecture verdict

This is the right level for what you're doing now.

Your actual SIH concept is bigger—the submitted material describes a platform that turns “Search → Read → Compare → Verify” into “Describe → Get the right standards → See the evidence.”

The mobile app does not need to implement that entire backend to communicate the concept. It needs to make the interaction believable, visually polished, and internally consistent.

The most important thing is that the judge can perform this in under two minutes:

enter tender → see standards → inspect evidence → build specification → change a parameter → see conflict.

That is the demo. Everything else is noise.
